## Фаза 1 — Комнаты и синхронизация на FakeProvider

Порядок важен: сначала ядро синхронизации и его измерение, потом всё остальное.

### Бэкенд: домен
- [x] `PlaybackState` + чистая функция ожидаемой позиции; unit-тесты
- [x] Модель очереди (add / play_next / play_now / remove / move / shuffle / clear / repeat), история; unit-тесты
- [x] Актор комнаты: последовательная обработка команд (asyncio-очередь на комнату), `version`, `expectedQueueItemId`, антидребезг next/prev
- [x] Барьер старта трека (ready от разблокированных онлайн-участников, таймаут 2.5 с, старт `now + 300 мс`); play/seek с задержкой 150–200 мс; unit-тесты с внедрённым временем
- [x] Серверный таймер окончания трека → переход по очереди с учётом повтора
- [x] Статистика drift по комнате (медиана/p95 по участникам)
- [x] Rate limit команд на пользователя (5/с)

### Бэкенд: инфраструктура
- [x] SQLAlchemy 2 async модели: users, sessions, rooms, room_members, queue/state snapshot; Alembic миграция
- [x] Сессии на cookie (httpOnly, Secure, SameSite=Lax, 30 дней, скользящее продление), dev-логин без Яндекса
- [x] REST: `/api/auth/dev-login`, `/api/auth/me`, `/api/auth/logout`, `/api/rooms` (создать/мои), `/api/rooms/{slug}`
- [x] Генерация slug комнаты (неугадываемый, человекочитаемый)
- [x] WS `/ws/rooms/{slug}`: аутентификация по cookie, проверка Origin, лимит размера, валидация Pydantic, `clientMsgId` → `ack`/`error`
- [x] Протокол: все сообщения из §7.4 (кроме чата — фаза 4)
- [x] Сохранение состояния комнат в БД с дебаунсом, восстановление при старте (в паузе)
- [x] `MusicProvider` интерфейс + `FakeProvider` (метаданные + локальные аудиофайлы, `/api/stream/{trackId}` для fake)
- [x] `scripts/gen_fake_audio.py`: ffmpeg-генерация тонов со щелчками раз в секунду и голосовыми/тональными метками, разной длительности
- [x] Генерация JSON Schema протокола → TS-типы (`npm run gen:types`), проверка актуальности в CI

### Фронтенд: движок синхронизации (`src/player/`, чистый TS)
- [x] Абстракции: `Clock` (monotonic + epoch), `AudioOutput` (интерфейс над `<audio>`), `Scheduler`
- [x] `ClockSync`: 8 пингов, offset по медиане 3 лучших RTT, повтор каждые 30 с и после переподключения, сглаживание; unit-тесты с выбросами
- [x] `DriftController`: мёртвая зона, пропорциональный `playbackRate` 0.95–1.05, жёсткий seek ≥ 1 с, не чаще раза в 2 с, «нестабилен» после 3 неудачных seek, профили платформ, устойчивость к пропущенным тикам; unit-тесты
- [x] `outputLatency`/`baseLatency` как поправка
- [x] `SyncEngine`: применение `PlaybackState` (по version), запуск в момент `anchor` (таймер + доводка), барьер (`ready{version}`), опоздавшие стартуют сами
- [x] Два `<audio>` (текущий + следующий), предзагрузка за ~20 с до конца, переполучение протухшей ссылки
- [x] Обработка `waiting`/`stalled` (догоняет сам)

### Фронтенд: приложение (базово)
- [x] API-клиент, TanStack Query, Zustand-стор комнаты
- [x] WS-клиент: reconnect с экспоненциальной задержкой + джиттер (до 10 с), снапшот, офлайн-индикатор
- [x] Страницы: вход (dev-login), «Мои комнаты» + создание, комната `/r/{slug}`
- [x] Комната: плеер (обложка, прогресс, кнопки), кнопка «Включить звук», очередь (базово), поиск по FakeProvider (базово), участники со статусами
- [x] Отладочная панель (`?debug=1` / `D`): offset, RTT, drift, rate, буфер, version, output latency, медиана/p95 по комнате
- [x] Тестовый хук `window.__syncProbe` для e2e

### Тесты
- [x] Интеграционные: несколько WS-клиентов на FakeProvider — подключение, снапшот, команды, двойной next, переподключение, рестарт сервера с восстановлением
