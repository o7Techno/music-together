# DECISIONS — журнал решений и отступлений от ТЗ

Формат: **что решено** · почему · альтернативы. Отступления от `SPEC.md` помечены **[отступление]**.

---

## D-001. Таск-раннер — корневой `package.json` вместо `make`
- **Решение:** `npm run dev`, `npm run check` и т.д. в корневом `package.json` (+ `concurrently`).
- **Почему:** ТЗ допускает «`make dev` или аналог»; основная машина разработки — Windows без `make`.
  Node всё равно обязателен для фронта, npm-скрипты работают одинаково на Windows/Linux/macOS/CI.
- **Альтернативы:** Makefile (нет на Windows из коробки), `just` (ещё одна зависимость), `tasks.py`.

## D-002. TypeScript 6.0, а не 7
- **Решение:** `typescript@~6.0`.
- **Почему:** шаблон Vite ставит TS 7 (нативный порт), но `typescript-eslint` поддерживает TS < 6.1,
  а ТЗ требует ESLint. Шаблонный `oxlint` заменён на ESLint + Prettier по ТЗ.
- **Пересмотреть:** когда typescript-eslint объявит поддержку TS 7.

## D-003. React 19 (ТЗ: «React 18+»)
- Текущий стабильный, совместим со всеми библиотеками стека. Требованию «18+» удовлетворяет.

## D-004. `yandex-music[async,crypto]`
- **Решение:** extras `async` (aiohttp — без него `ClientAsync` не работает) и `crypto`.
- **Прокси:** библиотека пробрасывает `proxy_url` в aiohttp, который нативно умеет только HTTP(S)-прокси.
  Для `socks5://` понадобится `aiohttp-socks` — добавлю в фазе 2 вместе с `YM_PROXY_URL`.

## D-005. Device Flow — средствами библиотеки
- `yandex-music` 3.2.2 умеет OAuth Device Flow пошагово: `request_device_code()` и
  `poll_device_token()` (client_id/secret официального Android-приложения Яндекс Музыки).
  Это ложится ровно на `/api/auth/device/start` + `/api/auth/device/poll` без своей реализации протокола.
- Проверено без токена из NL: код из 8 символов, страница `https://ya.ru/device`, срок жизни кода 300 с,
  рекомендованный интервал опроса 5 с. Ответ содержит `refresh_token` → можно обновлять токен.

## D-006. Предупреждение Starlette про `httpx` в TestClient — отфильтровано
- Starlette предлагает сторонний пакет вместо `httpx`; ставить неизвестную зависимость ради теста
  не стал, предупреждение отфильтровано в `pytest` (`filterwarnings`).

## D-007. Аудио: `get-file-info`, `transport=raw`, только браузерные кодеки
- **Решение:** `tracks_file_info(track_id, quality="hq", codecs=["aac-mp4","he-aac-mp4","mp3","aac","he-aac"], transport="raw")`.
  `encraw` (AES-CTR) не используем никогда — браузер его не сыграет, а расшифровка на сервере = раздача аудио.
  Фоллбэк — старый `download-info` + `get_direct_link` (mp3).
- **Почему:** спайк (docs/yandex-spike.md): raw-файлы — обычные MP4/AAC и MP3 192 кбит/с, играют в
  Chrome/Edge/Firefox с перемоткой. FLAC сервер не отдал ни разу; к тому же он тяжелее и хуже с Safari.
- Ответ содержит 4 зеркала `urls[]` → клиент при ошибке сначала пробует следующее зеркало, потом
  просит новую ссылку у бэкенда.

## D-008. Режим аудио по умолчанию — `direct`
- Ссылка выдаётся только запросившему пользователю (получена его токеном), браузер играет её напрямую.
- **Риск:** привязка ссылок к IP не проверена (у меня один исходящий IP). Проверка — ручной QA фазы 2
  (сервер на VPS в РФ, браузер у владельца). Если привязка есть — `AUDIO_MODE=proxy`, код готов к обоим.

## D-009. `<audio>` без `crossOrigin`, без Web Audio на медиаэлементе
- С `crossOrigin` старые `get-mp3` ссылки не играют (403 на Origin), в Chromium ломались и `strm`.
  Синхронизации Web Audio не нужен: `outputLatency`/`baseLatency` берём из отдельного `AudioContext`.

## D-010. «Нужна подписка» определяем по `quality == "preview"`
- Без Плюса `get-file-info` не падает, а отдаёт 30-секундное превью. Такой ответ → ошибка
  «нужна подписка Плюс» / «трек недоступен», превью никогда не играем.

## D-011. Токен Яндекса: храним и refresh_token
- Device Flow отдаёт `access_token` (1 год) + `refresh_token`. Оба шифруем (MultiFernet), обновляем
  access_token заранее (за 7 дней до истечения) и при `UnauthorizedError` — одна попытка refresh,
  затем — «войдите заново».

## D-012. UX входа: показывать, каким аккаунтом выполнен вход
- В спайке владелец подтвердил код не тем аккаунтом (без Плюса). Поэтому: на экране Device Flow —
  подсказка «войдите в аккаунт с Плюсом», после входа без Плюса — имя аккаунта и кнопка
  «Войти другим аккаунтом».

## D-013. Прокси для Яндекса — `YM_PROXY_URL` (только HTTP/HTTPS, см. D-026)
- Реальный прокси не проверен (нет у владельца); VPS будет в России, прокси не нужен.

## D-014. Остановка после фазы 0 пропущена по указанию владельца
- Владелец после получения токена написал «делай весь проект дальше». Результаты спайка оформлены
  в docs/yandex-spike.md, работа продолжена без паузы.

## D-015. Код «переподключитесь» при остановке — 1012 от uvicorn
- При graceful shutdown uvicorn сам закрывает WebSocket кодом **1012 (Service Restart)** до
  lifespan-shutdown, поэтому наш `closed{reason:"restart"}` (4012) не успевает уйти. Клиент трактует
  1012 и 4012 одинаково: переподключение без экспоненциальной паузы. Состояние комнат при этом
  сохраняется в lifespan-shutdown (проверено интеграционным тестом рестарта).

## D-016. Очередь рассылается целиком, а не патчами
- ТЗ допускает «полная очередь или патч с версией». Для масштаба пет-проекта (≤ 2000 элементов,
  ≤ 10 человек) полная очередь с `version` проще и надёжнее; клиент игнорирует устаревшие версии.

## D-017. Seek во время воспроизведения — через короткий барьер
- Сервер переводит состояние в `loading` на целевой позиции, ждёт `ready` не дольше 1 с и стартует
  через 150 мс. Сервер не знает, что у клиента в буфере, поэтому «короткий барьер при перемотке
  за пределы буфера» реализован единообразно: если данные в буфере, `ready` приходит за десятки мс.

## D-018. Интеграционные тесты — на живом uvicorn + SQLite
- Реальный сервер в фоновом потоке, клиенты `websockets`/`httpx` с таймаутами: проверяются lifespan,
  настоящие WS-коды закрытия и рестарт с восстановлением. SQLite вместо PostgreSQL — ради скорости
  и отсутствия внешних зависимостей; типы моделей переносимы, миграции проверяются на PostgreSQL
  (`alembic check` локально и в CI).

## D-019. Пустая комната: первый добавленный трек начинает играть сразу
- Если ничего не играет и в очередь добавили треки, первый сразу запускается (через барьер).
  Это ожидаемое поведение «добавил — заиграло»; на паузе стоит только восстановленная комната.

## D-020. `erasableSyntaxOnly` в tsconfig выключен
- Флаг из шаблона Vite нужен только для запуска TS через type-stripping в Node; сборка идёт через
  Vite/esbuild. Без него доступны параметрические свойства конструкторов — короче и привычнее.

## D-021. Компенсация задержки вывода звука по умолчанию выключена [отступление]
- ТЗ: «учитывать `outputLatency`/`baseLatency`, если браузер отдаёт». `currentTime` медиаэлемента
  в Chromium и Firefox уже отражает позицию, отданную аудиоустройству (рендерер учитывает задержку
  своего вывода), а `AudioContext.outputLatency` относится к графу Web Audio, а не к `<audio>`.
  Вычитать её из `currentTime` — риск двойной компенсации и рассинхрона между браузерами.
- Сделано: задержка вывода измеряется и показывается в отладочной панели, компенсация включается
  переключателем там же. Решение о значении по умолчанию — по ручной проверке «на слух» на реальных
  устройствах (docs/manual-qa.md); если подтвердится польза — включим для конкретных платформ.

## D-022. Мягкие пороги e2e-синхрона в CI
- Локально e2e проверяет цели §5.1 (медиана ≤ 30 мс, p95 ≤ 80 мс). На shared-раннерах GitHub
  (2 vCPU на три браузерных контекста плюс бэкенд и Vite) — медиана ≤ 50 мс, p95 ≤ 150 мс,
  чтобы тест не флапал из-за шумных соседей. Фактические цифры пишутся в артефакт `sync-stats.json`.

## D-023. Dev-логин и FakeProvider вместе
- Вход без Яндекса доступен, если `MUSIC_PROVIDER=fake` или окружение не prod. Пользователи dev-логина
  всегда работают через FakeProvider, даже если сервер настроен на Яндекс (локальная разработка без
  аккаунта). В проде с `MUSIC_PROVIDER=yandex` dev-логин выключен.

## D-024. Сессия комнаты — внешний стор, а не состояние компонента
- `RoomSession` (WS + движок + `<audio>`) создаётся/закрывается эффектом страницы и хранится в
  маленьком Zustand-сторе. Так нет `setState` внутри эффекта, и двойной вызов эффектов StrictMode
  корректно закрывает первую сессию.

## D-025. Прокси-режим: короткоживущая ссылка на апстрим на пару (пользователь, трек)
- Браузер при перемотке шлёт серию Range-запросов; без запоминания каждый стоил бы запроса к API
  Яндекса. Ссылка хранится в памяти до 10 минут **только для того же пользователя и трека** — это не
  кеш аудио и не общий кеш (SPEC §6.2 соблюдён). Аудио идёт потоком, на диск не пишется. Лимит —
  4 одновременных потока на пользователя. При 4xx от апстрима ссылка переполучается.

## D-026. SOCKS-прокси для Яндекса не поддерживается [отступление]
- `yandex-music` передаёт `proxy_url` в `aiohttp.request(proxy=…)`, а aiohttp умеет только HTTP(S)
  прокси; своего коннектора библиотека подключить не даёт. ТЗ допускает «HTTP/SOCKS» — поддержан HTTP(S).
  Сервер будет в России, прокси не нужен; при необходимости — HTTP-прокси или подмена Request.

## D-027. Токен: вход по ссылке Device Flow через официальное приложение Яндекс Музыки
- client_id Device Flow — официального Android-приложения (как в библиотеке). Если Яндекс ограничит
  его для сторонних устройств, останется вход по токену; инструкция на экране входа ведёт на
  OAuth implicit flow того же приложения.

## D-028. Остановка после фазы 2 — сводная ручная проверка в конце
- Владелец после фазы 0 попросил «делать весь проект дальше». Поэтому после фазы 2 работа
  продолжена; всё, что требует реальных аккаунтов/устройств (Device Flow в браузере, второй аккаунт,
  привязка ссылок к IP на VPS, iOS), собрано в docs/manual-qa.md. Автоматически проверено:
  вход по токену, поиск, добавление по ссылке, воспроизведение и синхрон двух вкладок на реальном
  Яндексе (docs/yandex-spike.md §8).

## D-029. Диалоги — нативный `<dialog>`, без Radix/shadcn [отступление]
- ТЗ: «Radix UI или shadcn/ui для примитивов». Нужны только модальный диалог (вставка ссылки,
  подтверждение очистки) и вкладки. Нативный `<dialog>` с `showModal()` даёт фокус-ловушку, Esc и
  `::backdrop` без зависимостей; вкладки — простой `role="tablist"`. Это экономит бандл (бюджет
  < 300 КБ gzip) и не ухудшает доступность. Если понадобятся меню/поповеры — подключим Radix точечно.

## D-030. Enter в поиске до прихода результатов выполняется отложенно
- Пользователь часто печатает и сразу жмёт Enter. Чтобы не добавить трек из результатов предыдущего
  запроса, Enter запоминается и срабатывает, когда придут результаты именно набранного текста.

## D-031. Undo удаления — повторное добавление на ту же позицию
- «Отменить» отправляет `queue.add` с `index` исходной позиции и `source.kind = "undo"`: в ленте
  событие не дублируется, у элемента новый id (это новый элемент очереди с тем же треком).

## D-032. `/api/auth/session` для анонимов вместо 401 от `/api/auth/me`
- Главная проверяет, вошёл ли пользователь. 401 от `/me` браузер пишет в консоль как ошибку
  (минус в Lighthouse best practices и шум при отладке). `/session` всегда отвечает 200 с `me: null`
  для анонимов; `/me` остаётся строгим для API-клиентов.

## D-033. Мобильная раскладка — одно дерево компонентов, вкладки через CSS
- Панели «Очередь / Добавить / Люди» — те же компоненты, что на десктопе, переключаются классами;
  плеер и чат на мобильных монтируются отдельно (мини-плеер + разворачиваемый лист), чтобы на
  странице не было двух одинаковых плееров. Брейкпоинт — 1024 px (`useIsDesktop`).

## D-034. Подтверждение «выгнать участника» — `window.confirm`
- Редкое разрушительное действие только для создателя; системный диалог доступен и не требует
  отдельного компонента. Остальные подтверждения — нативный `<dialog>` (D-029).

## D-035. Docker-образы и `docker compose up` проверяются в CI
- На машине разработки демон Docker перестал отвечать в фазе 5, а перезапускать Docker Desktop
  пользователя без спроса не стал. Job `docker` в GitHub Actions собирает оба образа, поднимает
  `docker compose up -d --wait` с `DOMAIN=localhost` (внутренний CA Caddy) на FakeProvider и по HTTPS
  проверяет `/health`, `/ready`, страницу, CSP-заголовок, вход, создание комнаты, поиск и сохранность
  данных после рестарта бэкенда. Реальный домен и Let's Encrypt — при первом деплое владельцем.

## D-036. DSN Sentry для фронта отдаётся сервером
- Чтобы один образ фронта работал в любом окружении, `SENTRY_FRONTEND_DSN` приходит в
  `/api/auth/config`, а SDK подгружается отдельным чанком только при заданном DSN (основной бандл
  не растёт). DSN фронта публичен по своей природе.

## D-037. `.env.example` — с продакшен-значениями по умолчанию
- Его копируют на сервер (`scripts/init-env.sh` подставляет домен и секреты). Локальная разработка
  работает без `.env`: значения по умолчанию в `Settings` — dev/FakeProvider/localhost.

## D-038. Первый деплой: образы собираются на сервере, Caddy — только после смены DNS
- **Решение:** `docker compose build` на самом VPS, без реестра образов. Сервер: Ubuntu 24.04, 1 vCPU
  (гарантированная доля 10 %), 2 ГБ RAM + swap 2 ГБ, HDD 20 ГБ; каталог `/opt/music-together`; лимит
  логов контейнеров в `/etc/docker/daemon.json`; бэкап по cron в 04:15, пока только на этом же сервере.
- **Почему:** 2 ГБ с подкачкой хватило, сборка заняла около минуты; реестр усложнил бы деплой без пользы.
  Caddy не запускаем до смены A-записи, чтобы не тратить попытки выпуска сертификата Let's Encrypt.
- **DNS:** зона домена в карточке домена reg.ru (`ns1/ns2.reg.ru`); панель хостинга ispmanager не участвует.
  Сертификат выпускается только для домена без `www`.
- **Осторожно:** не запускать временный веб-сервер из каталога проекта на проде — он раздаст `.env`.
- **Хостинг:** Cloud.ru. Порты 80 и 443 открываются в группе безопасности машины; без этого Let's Encrypt
  получает `Timeout during connect`. После открытия правило заработало не сразу: сертификат выдан с повтора.
- **Состояние на 2026-10-31:** сайт работает по HTTPS, сертификат Let's Encrypt выдан. Не проверено:
  вход через Яндекс на проде, воспроизведение и привязка аудиоссылок к IP (D-008). IP и логин сервера в
  репозиторий не записываем: репозиторий публичный.
- **Альтернативы:** сборка в GitHub Actions и реестр GHCR — нужна при 1 ГБ RAM.

## Моя волна

## D-039. Ревью `SPEC-wave.md` по коду; вопросы владельца — на остановке после спайка
- ТЗ писалось без доступа к коду. Ревью сверило его с кодом и исходниками `yandex-music` 3.2.2, но без
  вызовов реального API, поэтому всё про поведение Яндекса подтверждает спайк. Изменения, риски и вопросы —
  `SPEC-wave.md` §15, архитектура и план — §13–14а. Решения реализации записывать сюда же.

## D-040. Ответы владельца после спайка волны
- Пока владелец офлайн, фидбек не отправляется. Общая волна без участников ждёт, а не останавливается.
  Остановить и заменить чужую волну может любой участник. «Следующий» не ограничен: `skips_per_hour: 6`
  приходит от API, но 10 `skip` подряд приняты; ошибки отправки только в лог.
- **Два PR:** `feature/my-wave` — коллекция, волна участника и по зерну, настройки; `feature/shared-wave`
  поверх него — общая волна (§3.2).
- Подход — сессионный API ротора (`docs/wave-spike.md`). Классический API не реализуем: он не нужен.

## D-041. 403 от Яндекса отдельно не обрабатываем
- `SPEC-wave` §14 п. 2 предлагал отличать запрет на конкретный ресурс от невалидного токена. В спайке 403 не
  встретился, а библиотека не отличает его от 401. Волна останавливается по `ProviderAuthError`: при
  успешном обновлении токена `_call` просто повторяет запрос, токены стираются только при неудачном обновлении.

## D-042. Плейлисты — нативный `<dialog>`, вместо меню — кнопки в строке [отступление]
- `SPEC-wave` §6.2 и §9 просит контекстное меню и поповер. Сделано: ♥ и «в плейлист» — кнопки в строке, выбор
  плейлиста — один модальный `<dialog>` на комнату. Как и D-029, без новой зависимости и с нормальной работой на
  телефоне. На узком экране в строке только «в плейлист», а ♥ находится в этом диалоге: места мало.
- Волна по зерну запускается из панели «Волна» («От того, что играет», настроения, занятия, жанры), а не из меню
  каждой строки: так не нужен выбор трека в сотнях строк. Подтверждение замены волны — `window.confirm` (D-034).
- Значения настроек передаются сидами; значение «по умолчанию» не отправляется.

## D-043. Трек проверяется токеном владельца при приёме порции, а не перед постановкой
- `SPEC-wave` §7 допускает проверку перед постановкой следующим. Драйвер проверяет всю порцию (5 запросов
  `get_stream`, около 100 мс каждый): в буфер не попадает то, что владелец не услышит, и `nextTrackId` не
  меняется в последний момент, когда клиенты уже предзагрузили трек.
- Автопропуск трека, недоступного всем слушателям (предложение из ревью), не реализован: в спайке недоступных
  треков волны не встретилось, а значит, и защищаться пока не от чего. Известное поведение — тишина на весь трек.
