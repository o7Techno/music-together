## 1. Что хотим

Любой участник может включить в комнате **волну** — бесконечный поток рекомендаций Яндекс Музыки, который вся комната слушает синхронно, как обычную очередь. Волна подстраивается под то, что комната дослушивает и пропускает. Ручное добавление треков продолжает работать и сочетается с волной.

Кроме того, каждый участник может прямо из комнаты сохранить понравившийся трек в свою коллекцию: лайкнуть его (добавить в «Мне нравится») или добавить в любой свой плейлист — для любого трека, не только из волны.

### Термины
- **Владелец волны** — участник, чьим токеном запрашиваются треки. В коде `wave_owner_id` / `source_user_id`. Не путать с **создателем комнаты**: `Room.owner_id`, `MemberView.is_owner`, `RoomInfo.owner_id` уже заняты им.
- **Буфер волны** — будущие треки на сервере, ещё не попавшие в `Queue`.
- **Источник** — волна одного участника. В режимах 3.1 и 3.3 один источник, в 3.2 — несколько.

## 3. Режимы волны

### 3.1. Волна участника (основной режим)
- Кнопка «Включить мою волну». Нажавший становится **владельцем волны**: треки запрашиваются его токеном, фидбек уходит в его аккаунт.
- Остальные участники воспроизводят эти же треки **своими** токенами (как и любой трек очереди — без изменений в получении аудио). **[есть]**: `SyncEngine` → `GET /api/stream/{track_id}` → провайдер текущего пользователя.
- В плеере видно: «Моя волна · {имя владельца}».
- Если волна уже играет и кто-то другой включает свою — диалог «Заменить волну {имя} на свою?»; при подтверждении — замена с событием в ленте. Подтверждение проверяет сервер: `wave.start` несёт `expected_wave_id`, устаревший → `ConflictError` (`code=stale`). Так два одновременных нажатия не заменят волну молча.
- Запустить волну может только участник с Плюсом (`users.has_plus`), иначе `SubscriptionRequiredError`. Без Плюса владелец не услышит собственные треки.

### 3.2. Общая волна (смешанная)
- Кнопка «Общая волна»: в поток по очереди (round-robin) попадают треки из волн всех участников, которые согласились в ней участвовать (переключатель «Моя волна участвует» у каждого, по умолчанию включён у онлайн-участников с разблокированным звуком и Плюсом).
- Каждый трек запрашивается токеном и учитывается в фидбеке того участника, из чьей волны он пришёл. У трека в UI — аватар «чья волна».
- Участники, ушедшие офлайн, выпадают из ротации; вернувшиеся — снова попадают. Выпадение — после `LEAVE_GRACE_MS` (15 с, уже есть в `Room`), чтобы перезагрузка вкладки не дёргала ротацию. Треки выпавшего из буфера убираются, а текущий доигрывает.
- Дубликаты между волнами отфильтровываются.
- Если источников не осталось — событие «В общей волне никого нет», волна в состоянии `waiting` и оживает, когда кто-то вернётся. Сама не выключается: правило 15 минут из раздела 7 относится к одному владельцу. Подтвердить: вопрос 2 в разделе 15.2.
- Ротация не требует, чтобы запустивший оставался в комнате.

### 3.3. Волна по зерну
- Запуск волны от текущего трека, исполнителя, альбома, жанра или настроения/занятия (в зависимости от того, что подтвердил спайк). Доступно из меню трека/артиста и из панели «Волна». Владелец — нажавший.
- Сервер принимает зерно как `{kind, id}` и сам собирает сид. **Сырую строку сида от клиента не передавать в API.**

### 3.4. Настройки волны
- Настройки, которые поддерживает API (например, характер «любимое / незнакомое / популярное», настроение, язык), меняет владелец волны. Для общей волны — любой участник, применяется ко всем источникам, если API позволяет; иначе — каждый к своей.
- Смена настроек создаёт новую сессию и сбрасывает буфер; текущий трек доигрывает. Команды чаще раза в 2 с схлопываются (последняя побеждает), иначе ползунок породит серию сессий.
- Список значений — из `rotor_wave_settings`, кешируется у провайдера на 15 минут. UI строится по ответу, значения в коде не прописывать.

## 4. Волна и очередь

- Волна — это **источник автопродолжения**, а не сотни треков в очереди. Буфер живёт отдельно от `Queue.upcoming`: очередь рассылается целиком (D-016), а `queue.shuffle` и `queue.clear` не должны трогать волну.
- Порядок по умолчанию: треки, добавленные вручную, имеют приоритет — следующий трек берётся из ручной очереди, пока она не пуста; когда она пуста — из волны. Альтернативный режим (переключатель в настройках комнаты): «ручные треки вставляются между треками волны через один». Решение по умолчанию задокументировать. Переключатель виден создателю комнаты: `RoomSettingsButton` уже показывается только ему.
- В UI отдельная секция «Дальше в волне» (3–5 ближайших треков) под ручной очередью. Для трека из волны: «закрепить в очередь» (перенести в ручную очередь), «убрать» (не играть; для волны считается пропуском без прослушивания, если API это поддерживает, иначе просто удаляется из буфера).
- Закреплённый трек — обычный ручной элемент очереди: `added_by` = закрепивший, без событий фидбека. Батч у него уже не актуален.
- Кнопка «Остановить волну»: текущий трек доигрывает, дальше — только ручная очередь (или пауза, если она пуста). Как и остальное управление, доступна любому участнику (`SPEC.md` 4.2). Вопрос 3 в разделе 15.2.
- Ручное «играть сейчас» во время волны не выключает волну: после ручного трека (и ручной очереди) волна продолжается. Прерванный трек волны получает `skip` с фактическим временем.
- Не повторять треки, сыгранные в комнате за последние 100 треков. **[изменено]** `Queue.history` хранит только 50 (`HISTORY_LIMIT`), поэтому нужен отдельный `recent_track_ids: deque(maxlen=100)` в состоянии волны. Его же передавать в параметр `queue` при запросе порции, обрезав до размера, который подтвердит спайк.

### 4.1. Синхронизация не должна ухудшиться

Это главный риск фичи. Существующий код требует следующего.

1. **Предзагрузка сейчас не увидит волну.** `SyncEngine.maybePreload` читает только `queue.upcoming[0]`. Без правки каждый переход на трек волны пойдёт через холодную загрузку и таймаут барьера.
   **[изменено]** Клиент не повторяет логику выбора следующего трека: сервер считает её сам и присылает в поле `next_track_id` сообщения `wave` (раздел 8). Движок использует `queue.upcoming[0]`, только если волна неактивна. Иначе режим «через один» пришлось бы дублировать на клиенте.
2. **Сроки.** Сервер должен знать следующий трек **не позже чем за 30 с до конца текущего**; `PRELOAD_BEFORE_END_MS` = 20 с не меняется. Буфер держит минимум 3 трека. Дозапрос — при старте каждого трека и при падении буфера ниже порога. Короткий трек поэтому не ломает сроки: следующий уже в буфере.
3. **Не трогать `PlaybackState.version` ради волны.** Каждая новая версия вызывает `SyncEngine.applyState`: отмену старта, сброс контроллера дрейфа, паузу запасной деки. Пополнение буфера, смена настроек и закрепление шлют только `wave`/`queue`, но не `playback`.
4. **I/O только вне `room.lock`.** Запрос порции идёт в фоновой задаче, результат применяется под `lock` с проверкой `generation` (см. 13.2): ответ от заменённой или остановленной волны отбрасывается. Иначе медленный Яндекс заблокирует все команды комнаты.
5. **Не блокировать цикл чтения WS.** `_dispatch` в `ws/endpoint.py` обрабатывает сообщения соединения по одному: `await` запроса к Яндексу задержит `ping` и `ready` этого клиента, исказит оценку часов и может сорвать барьер (`queue.add` уже так делает, но там действие редкое). `wave.start` и `wave.update_settings` только запускают фоновую задачу и сразу отвечают `ack`; ход запуска виден в `wave.status = starting`. Кроме того, одна попытка может занять около 30 с, а `COMMAND_TIMEOUT_MS` на клиенте — 10 с.
6. **Запасная дека может держать устаревший трек** после закрепления или смены настроек. Это безопасно: `ensureTrack` загрузит нужный, а `loadInto` перезапишет деку. Покрыть тестом, логику не усложнять.

### 4.2. Взаимодействие с существующей очередью

| Действие | Поведение с волной |
|---|---|
| `cmd.next` | Обычный `_advance`; выбор идёт через новую логику. Трек волны получает `skip` |
| `cmd.prev` | `Queue.previous()` ставит текущий в `upcoming[0]`: трек волны попадает в ручную очередь. Он получает `skip` и дальше считается ручным. Вернувшийся из истории трек волны **повторного фидбека не шлёт** |
| Трек из истории | Обычный ручной элемент (`queue.add`) |
| Повтор «трек» | Разрешён: волна ждёт. `trackFinished` уходит при первом естественном конце, повторы не считаются |
| Повтор «очередь» | **[изменено]** Несовместим: сыгранные треки возвращаются в `upcoming`, очередь никогда не опустеет, и волна не заиграет. `wave.start` сбрасывает повтор на `off` с событием в ленте, а `cmd.set_repeat(queue)` при активной волне даёт `ValidationError`. В `Player.tsx` цикл `NEXT_REPEAT` пропускает `queue`, пока волна активна |
| `queue.shuffle`, `queue.clear` | Только ручная очередь. Текст подтверждения не менять |
| Ничего не играет | `_cmd_play` при активной волне берёт трек из неё и не показывает «Очередь пуста». Если буфер пуст — `waiting`, старт при поступлении порции |
| Трек с `duration_ms <= 0` | Отфильтровать при приёме: `_schedule_end_timer` не поставит таймер, и комната зависнет |
| Комната опустела | **[есть]** `Room.leave` ставит паузу. Волна сохраняется, запросы порций и фидбек не идут |

## 5. Обратная связь в волну

### 5.1. События
- Фидбек отправляет **сервер** по фактическому воспроизведению в комнате, а не клиенты:
  - старт волны / сессии (`radioStarted`);
  - старт трека (`trackStarted`);
  - трек дослушан до конца (`trackFinished` с длительностью);
  - трек пропущен любым участником (`skip` с фактическим временем прослушивания).
- **[изменено]** «Волна остановлена» из исходного ТЗ не отправляется: такого события нет в API. Остановка просто прекращает запросы, текущий трек при этом получает свой `trackFinished` или `skip`.
- В общей волне каждое событие уходит владельцу источника конкретного трека.
- **Лайк** (подробно — раздел 6): если участник лайкает трек из своей же волны, лайк дополнительно уходит как фидбек этой волны.
- **«Не нравится»**: у любого участника — это пропуск трека (с фидбеком `skip` в волну источника). У владельца волны дополнительно — настоящий дизлайк в его аккаунт и событие `dislike` (с короткой подсказкой при первом использовании, что это повлияет на его рекомендации). Кнопка показывается только на треках волны. Для ручных треков есть обычный «Следующий».

### 5.2. Как считать секунды
Сервер знает не «сколько секунд сыграно», а только позицию; перемотка её искажает. **[изменено]** `Room` накапливает `played_ms` для текущего элемента волны: при каждом выходе из `playing` (`_pause`, `_seek`, `_load`) добавляет `now − max(anchor, момент старта)`.
- `trackStarted` — один раз на элемент, в `_finish_barrier`. Этот метод вызывается и после перемотки, поэтому нужен флаг, что элемент уже стартовал. После рестарта флаг восстанавливается.
- `played_ms` входит в сохраняемое состояние волны.
- При `natural_end=True` — `trackFinished`, иначе `skip`.

### 5.3. Настройка «не учить» и пока владельца нет
- Переключатель у каждого участника «Не учить мою волну на прослушиваниях в комнате» — тогда фидбек в его аккаунт не отправляется (с пометкой, что волна будет хуже подстраиваться). При первом включении своей волны — однократное пояснение, что волна будет учиться на вкусах всей комнаты (флаг в `localStorage`).
- **[предложение]** При включённом переключателе создавать сессию с `incognito=True`, если спайк подтвердит, что это работает. Это прямой механизм API; простое молчание может давать другую выдачу.
- Настройка действует и на текущую волну: при отправке читается заново.
- Явный дизлайк и лайк в коллекцию — личное действие и уходят всегда.
- Пока владелец офлайн (окно 15 минут), фидбек по умолчанию **не отправляется**: он не слушает, а его рекомендации меняются. Вопрос 1 в разделе 15.2.

### 5.4. Отправка
- Асинхронно, с ретраями; пачками через `rotor_session_feedbacks` либо вместе с запросом порции (`rotor_session_tracks(feedbacks=…)`). Ошибки фидбека логируются и **никогда** не ломают воспроизведение.
- Одна очередь на пользователя с ограничением размера (200 событий, при переполнении выбрасываются самые старые). При остановке сервера — попытка сброса не дольше 2 с, оставшееся теряется: фидбек не критичен, а `stop_grace_period` в compose — 20 с.
- `session_id` и `batch_id` хранятся только на сервере, в таблице «элемент → метаданные» состояния волны. **В `QueueItem` их не класть**: очередь рассылается клиентам целиком.

## 6. Лайки и добавление в плейлист

Функции работают для **любого** трека в комнате (текущий, ручная очередь, «Дальше в волне», история, результаты поиска, треки альбома/плейлиста) и всегда действуют на аккаунт **того, кто нажал**.

**[частично]** Уже есть: `GET /api/me/liked` (полные треки, не больше 2000, кеш 2 минуты), `GET /api/me/playlists`, поля `PlaylistSummary`, кнопки на строках в `HistoryList`, `QueuePanel`, `SelectableTrackList`, `SearchPanel`. Нет мутаций, статусов и общего компонента действий над треком.

### 6.1. Лайк («Мне нравится»)
- Кнопка ♥ в плеере и в меню каждого трека. Повторное нажатие — убрать из «Мне нравится».
- Состояние ♥ у каждого участника своё.
- **[изменено]** Вместо `GET …/status?trackIds=…`: `GET /api/me/liked/ids` отдаёт все id разом, клиент держит `Set` в кеше TanStack Query. Яндекс и так отдаёт только полный список, а в виртуализированных списках пачки по видимым трекам дали бы поток запросов при прокрутке. На сервере — кеш на пользователя (2 минуты, инвалидация при изменении). `get_liked_tracks` для этого не использовать: он обрезает до 2000 и догружает метаданные.
- Оптимистичное обновление в UI с откатом и тостом при ошибке (паттерн — `optimisticQueue`). Лайк уже лайкнутого идемпотентен.
- Горячая клавиша `L` — лайк текущего трека. В `usePlayerHotkeys` проверять `e.code === 'KeyL'`: так работает и в русской раскладке. Media Session не обязательно.
- В ленте комнаты — «Аня лайкнула трек» (переключатель в настройках комнаты, по умолчанию включён); на текущем треке — маленький счётчик/аватары тех, кто его лайкнул.
- Анлайк и быстрое повторное нажатие событий в ленту не дают: не чаще одного события на пару (пользователь, трек) за элемент очереди.
- Счётчик живёт в памяти комнаты и сбрасывается при смене элемента. Он считает только лайки, поставленные в этой комнате на этом элементе, а не всю коллекцию участников.
- Если трек из волны лайкнувшего — дополнительно событие `like` в его волну (раздел 5).

### 6.2. Добавление в плейлист
- В меню трека и в плеере — «Добавить в плейлист» → поповер со списком плейлистов пользователя (поиск по названию, недавно использованные сверху — `localStorage`) и пунктом «Создать новый плейлист» (ввод названия, создать и сразу добавить).
- В списке — только плейлисты, которые пользователь может менять (`owner.uid == uid`). `get_user_playlists` сейчас не фильтрует.
- **[изменено]** Новый плейлист создаётся приватным: у библиотеки по умолчанию `public`, а пользователь не ждёт, что сборка из комнаты станет публичной.
- **[изменено]** Дубликат проверяется при выборе плейлиста, а не заранее в списке: иначе каждое открытие поповера читало бы все плейлисты целиком. Сервер всё равно читает плейлист ради свежей ревизии; при дубликате отвечает `409 duplicate`, клиент спрашивает «Добавить ещё раз?» и повторяет с `allowDuplicate: true`. Если спайк покажет, что `users_playlists([kinds])` дешёвый, можно добавить предварительную пометку.
- Удаление трека из плейлиста из поповера (если трек там уже есть) — желательно. API удаляет по индексу, поэтому индекс ищется на свежей ревизии.
- Тост с результатом: «Добавлено в „Для дороги“» и ссылкой «Открыть в Яндекс Музыке».
- Конфликты ревизий плейлиста (плейлист изменили параллельно в приложении Яндекса) обрабатываются прозрачно: перечитать ревизию и повторить, до 3 попыток; пользователь ошибку видеть не должен. См. раздел 14, п. 3: сейчас конфликт неотличим от сбоя сети.
- Изменения одного плейлиста сериализуются `asyncio.Lock` на пару (пользователь, плейлист).
- Повтор после таймаута мог бы вставить трек дважды: при неясном исходе перечитать плейлист и проверить, а не повторять вслепую.
- У `Track.album_id` может быть `None`, а `insert` требует `album_id`: догрузить через `get_tracks`, иначе понятная ошибка.
- Список плейлистов **[есть]**: кешируется 2 минуты, нужно добавить инвалидацию. У `TTLCache` нет метода удаления.
- **Сохранить в плейлист целиком** (желательно): «Сохранить очередь в плейлист» и «Сохранить историю комнаты в плейлист» — в новый или существующий плейлист, с учётом лимитов API.
  - **[изменено]** Не «за сегодня»: `Queue.history` хранит последние 50 элементов без времени воспроизведения. Сохраняем эти 50.
  - **[изменено]** Вместо прогресса по трекам — одна операция `Difference.add_insert(at, [треки])`, разбитая на порции по лимиту из спайка. Это снимает и частоту запросов, и большую часть конфликтов. Прогресс показывать по порциям, только если их больше одной.
  - Источник треков — со стороны клиента (`trackIds`), как и в `queue.add`.

### 6.3. Общее
- Лайки и плейлисты — только личные действия: никто не может лайкнуть или добавить трек в плейлист другого участника. Обеспечивается тем, что все роуты работают через `Provider` текущего пользователя.
- Запросы учитываются в лимитах частоты к Яндексу (`RateLimiter` в `YandexProviderPool`, 8 запросов/с на пользователя) и новом `collection_limiter` в `AppContext`; ошибки переводятся в понятные сообщения.
- Для мутаций, кроме HTTP-лимита, действует правило: при `RateLimitedError` оптимистичное состояние откатывается.

## 7. Граничные случаи

- **Владелец волны ушёл из комнаты.** Волна продолжает играть до 15 минут (env `WAVE_OWNER_GRACE_S`, по умолчанию 900), затем источник волны останавливается с событием в ленте, ручная очередь продолжается. Если владелец вернулся раньше — ничего не прерывается.
  - «Ушёл» — закрылось последнее соединение пользователя (`Room._user_online`). Перезагрузка вкладки таймер отменяет.
  - В состоянии хранится `owner_left_at_ms` (epoch), а не только таймер: таймеры не переживают рестарт и выгрузку. При подъёме комнаты остаток пересчитывается, истёкшее срабатывает сразу при первом `join`.
  - Если опустела вся комната, волна стоит на паузе. Правило 15 минут считается и здесь: вернувшись через час, комната застанет волну остановленной, а текущий трек — на паузе.
  - Если остальные слушатели есть, а токен владельца работает, запросы порций продолжаются его токеном до истечения окна.
- **Владельца выгнали, он вышел из аккаунта или токен стал невалиден — волна останавливается сразу.**
  - Выгнали: хук в `Room.kick`.
  - **[изменено]** Выход: `POST /api/auth/logout` сейчас только удаляет сессию, а WS остаётся открытым. Нужно добавить `RoomManager.stop_waves_of(user_id)`, который пройдёт по загруженным комнатам. Комнаты, не загруженные в память, проверяются при подъёме: у владельца нет токена → волна снята.
  - Токен: `ProviderAuthError` при запросе порции. Различать с 403 от конкретного метода: см. раздел 14, п. 2.
- **Трек волны недоступен у владельца** — пропустить без проигрывания, взять следующий. При приёме порции отбрасывать `available=False`, а перед постановкой следующим проверять `get_stream` токеном владельца: одна проверка на трек. Недоступен у других участников — поведение как в основном ТЗ (тишина у них и плашка) **[есть]**.
- **[предложение] Трек недоступен у всех.** Сейчас комната молча отыграла бы его целиком: барьер никого не ждёт, а таймер идёт. Для треков волны: если все онлайн-слушатели с разблокированным звуком прислали `track_unavailable`, автоматически перейти к следующему. Защита от цикла — не больше 3 подряд, затем `waiting`.
- **Яндекс не отдал следующую порцию** — ретраи с бэкоффом (5 с, 15 с, 60 с, затем раз в 2 минуты); если буфер кончился — понятное событие («Волна временно недоступна»), переход на ручную очередь или пауза; автоматическое восстановление, когда API снова отвечает, с событием «Волна снова играет». Запросы при этом идут только если в комнате есть слушатели.
- **Сессия протухла** (`unknown_session` или `terminated`) — прозрачно создать новую с теми же сидами и `queue` из `recent_track_ids`; `radioStarted` не отправлять повторно, если спайк не покажет обратного.
- **Пустая порция или одни повторы** — считать ошибкой и уйти в тот же бэкофф, иначе дозапрос зациклится.
- **Реклама в выдаче** — брать только `Sequence.type == "track"` и `track is not None`.
- **Одновременные команды** (два человека включают волну, пропуск в момент дозагрузки буфера) — через существующий последовательный актор комнаты, `generation` волны, версии состояния, `expectedQueueItemId`. Двойной пропуск: второй получает `ConflictError` **[есть]**, а `skip` уходит один раз.
- **Смена состава во время `wave.start`.** Запрос ещё идёт, а нажавшего выгнали или он вышел: результат отбрасывается по `generation`.
- **Рестарт сервера** — состояние волны (режим, владелец/участники, настройки, буфер, идентификаторы сессии/батча) сохраняется и восстанавливается; если сессия ротора протухла — прозрачно создаётся новая. Комнаты поднимаются лениво при первом `join`, поэтому волна «оживает» с первым подключением и на паузе (**[есть]** `persisted_playback`).
- **Выгрузка простаивающей комнаты** (`evict_idle`, 30 минут) — то же сохранение. `Room.close_all` должен отменять таймеры волны, а фоновые задачи — проверять `room.closed`.
- **Откат версии.** `ApiModel` использует `extra="forbid"`: старый код не прочитает состояние с новыми полями (`room_state_corrupted`). Откат с `main` после релиза волны потеряет очередь в активных комнатах. Описать в `docs/pr-my-wave.md`; перед деплоем сделать `scripts/backup.sh`.
- Лимиты частоты запросов к Яндексу на пользователя учитывают запросы волны **[есть]** в `YandexProvider._throttle`. Он ждёт не больше секунды и бросает `ProviderError`: для фоновых задач это повод для бэкоффа, а не для остановки.

## 13. Архитектура для этого кода

### 13.1. Куда что ложится

`Room` — чистый актор без I/O, знает только `RoomUser`. Токенов и провайдеров в нём быть не должно. Поэтому разделяем:

```text
rooms/wave.py          чисто: WaveState, выбор следующего, round-robin, дедуп, накопление played_ms,
                       решение «пора дозапросить». Без I/O и asyncio.
rooms/room.py          вызывает wave.py в _advance / _load / _finish_barrier / _pause / _seek / leave /
                       join / kick; команды wave.*; публикует WaveMessage; зовёт порт WaveDriver.
rooms/wave_driver.py   Protocol WaveDriver: request_batch(...), send_feedback(...), dislike(...).
                       Реализация: фоновые задачи вне lock, провайдер через ctx.providers,
                       свежий User из БД на каждый запрос, очередь фидбека на пользователя.
providers/*            новые методы; весь yandex_music только здесь.
```

- `Room.__init__` получает `wave_driver: WaveDriver | None = None`. Существующие тесты и `Env` не меняются.
- Выбор следующего — маленькая вставка: перед `queue.advance` при необходимости снять элемент с буфера и поставить в `upcoming[0]`. `Queue` при этом менять почти не нужно.
- `RoomManager` получает драйвер в конструктор. В `build_context` он создаётся после `ProviderFactory`.
- **Не использовать `User` из `room_socket`.** Этот объект прочитан при подключении и живёт часами. После обновления токена в нём старый `token_enc`, а пул сверяет отпечаток и пересоздаст провайдер со старым токеном. Драйвер читает `User` заново. Аналогичный риск уже есть в `queue.add` — см. раздел 15.3.

### 13.2. Поток данных

```text
wave.start → endpoint: ack, фоновая задача → provider.start_wave → под lock: if generation совпал → буфер
_advance → выбор → _load → барьер → _finish_barrier → trackStarted (один раз)
старт трека или буфер < 3 → driver.request_batch(generation) → под lock: дедуп, фильтры, буфер, WaveMessage
```

`generation` увеличивается при старте, замене, остановке и смене настроек.

### 13.3. Константы и настройки

```text
WAVE_BUFFER_MIN = 3              rooms/wave.py
WAVE_PREVIEW = 5
WAVE_RECENT_LIMIT = 100
WAVE_OWNER_GRACE_S = 900         core/config.py и .env.example
```

## 14. Подводные камни в текущем коде

1. **`account_uid` пуст.** `make_client` не вызывает `init()`, поэтому без `user_id` библиотека подставит `None` в URL (`/users/None/likes/...`). Все новые методы коллекции передают `user_id=self.uid`.
2. **403 считается `UnauthorizedError`.** `YandexProvider._call` на него запускает обновление токена. Флаг `_refreshed` одноразовый, поэтому повторный 403 станет `ProviderAuthError` «войдите заново». Запрет на конкретный плейлист или станцию не должен останавливать волну и разлогинивать. Для этих вызовов нужна своя обработка 403 — проверить в спайке, что реально приходит.
3. **Конфликт ревизий неотличим от сети.** Библиотека превращает 409 и прочие коды в `NetworkError`, а `_call` повторит запрос с той же ревизией и вернёт «Сервис недоступен». 400 станет `ProviderNotFoundError`. Для `users_playlists_change` нужен отдельный путь без слепых ретраев; конфликт различать по тексту или коду, которые установит спайк.
4. **Ретрай мутации небезопасен.** `_call` повторяет запрос при таймауте; для вставки в плейлист это возможный дубль (раздел 6.2).
5. **`TTLCache` без удаления.** Для инвалидации добавить `delete(key)`. Кеш `_private` живёт в экземпляре провайдера, а тот пересоздаётся раз в 30 минут и при смене токена.
6. **Новый `FakeProvider` на каждый вызов** (раздел 10).
7. **`users_likes_tracks` — весь список.** `get_liked_tracks` режет его до 2000.
8. **`QueueSource.kind` — закрытый `Literal`**: новый источник нужно добавить и туда.
9. **`ApiModel` — `extra="forbid"`** (раздел 7, откат версии).
10. **В режиме `AUDIO_MODE=proxy`** волна увеличит и трафик, и нагрузку на сервер. Привязка ссылок к IP до сих пор не проверена (D-008), прод — 1 vCPU с гарантированной долей 10 %.

### 15.3. Известные риски

- **Аккаунт.** Сервис работает через неофициальный API и `client_id` Android-приложения (D-027). Волна добавляет автоматическую активность от имени владельца с IP дата-центра, в том числе пока он не слушает. Реакция Яндекса неизвестна; для общей волны запросов больше. Минимизация: каждый только своим токеном, лимиты, без фоновых запросов в пустой комнате.
- **Качество рекомендаций.** Комната учит волну одного человека; отсюда пояснение и «не учить».
- **Неофициальность API.** Сессионный API и его события могут измениться; ошибка фидбека не должна затрагивать воспроизведение, а отказ порций переводит в «Волна временно недоступна».
- **Синхрон.** Если предзагрузка не сработает, каждый переход волны упрётся в барьер 2,5 с. Защита — тесты из раздела 10.
- **Нагрузка.** Прод скромный: 1 vCPU (гарантированная доля 10 %), 2 ГБ + swap, HDD. Волна в режиме `direct` почти не нагружает его. В режиме `proxy` с несколькими слушателями возможны проблемы — проверить до включения общей волны.
- **Привязка аудиоссылок к IP** не проверена на проде (D-008). Это блокер для реального QA волны; сначала закрыть `docs/manual-qa.md` §2.
- **Устаревший `User` в WS.** В `queue.add` уже есть этот риск; срабатывает только при обновлении токена прямо во время долгого соединения. Вне скоупа волны, но исправляется одной строкой при той же правке — при желании включить в шаг 7.
- **Откат после релиза** теряет состояние активных комнат (раздел 7). Перед деплоем — бэкап.
- **Вне проверки ревью.** Реальный API не вызывался: всё в разделе 2.1 взято из кода библиотеки и может отличаться от реального поведения.
