# Замеры рассинхрона

Как меряем (e2e `frontend/e2e/sync.spec.ts`): три независимых браузерных контекста Chromium в одной
комнате на FakeProvider; каждые 250 мс у всех берётся проба `window.__syncProbe()` — фактическая
позиция `<audio>` и ожидаемая по формуле сервера. Так как все клиенты считают позицию по одной
формуле, расхождение клиентов в один момент = разница их drift; **spread = max(drift) − min(drift)**
по трём клиентам. 30 с в установившемся режиме (после 2 с на сходимость).

Ограничение метода: меряется `currentTime` медиаэлемента, а не реальный звук из колонок. Задержка
вывода звука на разных устройствах — отдельная тема (DECISIONS D-021), проверяется вручную
(`docs/manual-qa.md`, проверка «на слух» щелчками FakeProvider).

## Результаты

| Дата | Окружение | Spread медиана | Spread p95 | Spread max | |drift| медиана | |drift| p95 |
|---|---|---|---|---|---|---|
| 2026-10-29 | Windows 11, Chromium headless, 3 контекста, локально | 10.6 мс | 19.0 мс | 29.4 мс | 6.5 мс | 13.1 мс |
| 2026-10-29 | то же, повторный прогон | 0.3 мс | 1.2 мс | 8.8 мс | — | — |

Цели SPEC §5.1 (десктоп): медиана ≤ 30 мс, p95 ≤ 80 мс — **выполнены с запасом**.

Прочее из того же прогона:
- пауза от одного участника применилась у всех за ~85–88 мс (включая 50-мс опрос теста; цель ≤ 300 мс);
- после перемотки spread за 3 с — в пределах цели (сходимость ≤ 1.5 с);
- клиент, отключённый на ~10 с (пока комната ставила паузу и снова запускала трек), после
  восстановления сети вернулся в синхрон.

Разброс между прогонами (10 мс vs 0.3 мс) объясняется тем, когда именно клиент стартовал
относительно 20-мс мёртвой зоны: внутри неё контроллер не трогает темп, и постоянное смещение
до ±20 мс считается «в синхроне» по замыслу ТЗ.
